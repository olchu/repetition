# План: голосовой AI-тьютор

Дата: 4 октября 2026. Основание: предоставленное техническое задание «Голосовой AI-тьютор для существующего учебного проекта». Статус: запланировано, реализация не начата. Связь с общим планом: [этап 6 кабинета ученика](STUDENT-NAVIGATION-PLAN.md).

## Цель и границы

Помочь ребёнку понять конкретный учебный материал перед тестом: **материал → голосовой разбор → устная проверка понимания → тест → результаты**. Основной источник тьютора — контекст выбранной темы. Тесты и кабинет дорабатываются в существующей архитектуре.

MVP включает запуск с темы, загрузку её контекста, разговор через OpenAI Realtime, педагогическое поведение, завершение, сохранение краткого структурированного резюме, просмотр родителем и переход к существующему тесту. Используется штатная голосовая модель OpenAI; отдельный TTS не нужен.

Визуальная концепция не выбрана. Названия кнопок ниже — рабочие. Отдельно предстоит определить точку входа, страницу или иной формат занятия, размещение истории и отчёта. Это не блокирует исследование проекта и подготовку модели данных.

## Исходное состояние и вопросы исследования

По `package.json` и `prisma/schema.prisma`: Next.js 16.3.4, Prisma 6.19, PostgreSQL; есть `User`, `ChildProfile`, `Subject`, версии `Test` по `stableId`, назначения и `Attempt`. В ТЗ `TestAttempt` соответствует существующей `Attempt`. Отдельных `Lesson`, `TutorSession`, `TutorUsage` и роли родителя сейчас нет. Содержимое теста хранится в `Test.content`; наличие исходного материала и его анализа в других частях проекта предстоит проверить.

Нельзя считать вопросник полноценной заменой учебного материала или автоматически считать администратора родителем. Доступность тьютора для старых тестов без источника и доступ родителя необходимо определить до реализации соответствующих функций.

## Шаг 2. Единый контекст учебной темы

- [ ] Переиспользовать анализ фотографий/PDF/текста при создании теста. При отсутствии такого процесса запланировать его добавление; не анализировать источник заново при каждом занятии.
- [ ] Подключить общий источник к генератору теста, если такой генератор существует, и к тьютору. При внешнем создании тестов определить способ импорта контекста вместе с тестом.
- [ ] Определить пустое состояние для теста без материала и способ его дополнения администратором.
- [ ] Подготовить миграции по правилам проекта: RLS без политик для новых таблиц `public`, подключения и проверки по [DEPLOY.md](DEPLOY.md).

Критерий: тьютор получает сохранённый материал конкретной доступной темы; запуск не повторяет распознавание источника. Ответы будущего теста не используются как сценарий подсказывания ребёнку.

- [ ] Добавить конфигурацию провайдера: серверный `OPENAI_API_KEY`, `OPENAI_REALTIME_MODEL`, `OPENAI_REALTIME_VOICE`. Перед реализацией проверить актуальную документацию OpenAI по WebRTC, временным credentials, событиям, usage и ограничениям сессий.
- [ ] Создать защищённый маршрут запуска: авторизация, доступ к теме, проверка лимитов, загрузка контекста, запись сессии и получение временных credentials. Рабочий контракт из ТЗ — `POST /api/tutor/session`; итоговый путь согласовать с существующими API проекта.
- [ ] Создать маршрут завершения (`POST /api/tutor/session/:id/finish` как рабочий контракт): проверка владельца, завершение, длительность, сохранение данных и запуск структурированного резюме.

- [ ] Настроить максимальную длительность сессии и дневной/месячный лимит; определить значения и субъект лимита, проверять их на сервере с учётом одновременных запусков.

Критерий: чужая тема/сессия недоступна, лимиты действуют при повторных и параллельных запросах, сессия корректно завершается при сбоях. Длительность не задаётся фиксированным двухчасовым уроком.

## Шаг 4. Голосовое занятие и педагогическое поведение

- [ ] Добавить действие «Разобрать тему с тьютором» в выбранной точке входа существующего учебного сценария.
- [ ] Подключить микрофон и OpenAI Realtime через WebRTC; воспроизводить голос модели в браузере, освобождать микрофон и соединение при завершении/уходе.
- [ ] Предусмотреть название темы, статус соединения, начало/завершение, состояния «говорит»/«слушает», mute и «Закончить и перейти к тесту».
- [ ] Обработать запрос и отказ доступа к микрофону, недоступное устройство, подключение, разрыв, ошибку, исчерпание лимита и завершение; обеспечить понятные действия и доступность на мобильном экране и с клавиатуры.
- [ ] Создать отдельный Tutor Mode prompt: спокойный преподаватель, короткое вступление, 1–3 диагностических вопроса, небольшие блоки объяснения, регулярная проверка понимания и язык по возрасту.
- [ ] Проверять понимание через пересказ, примеры, сравнение, причинно-следственные связи и применение в новой ситуации. После ошибки — наводящий вопрос, подсказка, повторная попытка; затем объяснение и повторная проверка.
- [ ] Поддержать перебивание и вопросы ребёнка, просьбы объяснить проще/повторить; после ответа возвращаться к теме. Связанные уточнения допустимы, значительные отклонения мягко ограничиваются.
- [ ] В конце проверять основные цели обучения. Рекомендация готовности к тесту не блокирует переход к нему.

Опционально после базового интерфейса: видимая транскрипция, таймер, отдельные кнопки «Объясни ещё раз» и «Объясни проще». Подробный production prompt уточняется после проверки базовой архитектуры.

Критерий: ребёнок может слушать, отвечать, перебивать, уточнять и закончить занятие; диалог помогает понять материал, а не превращается в длинную лекцию.

- [ ] Сохранять отчёт на сервере; отделять подтверждённые данные сессии от оценок модели. Ошибка резюме не должна терять завершённое занятие или блокировать тест.
- [ ] Предоставить родителю историю по ребёнку/теме: дата, длительность, обсуждённый материал, что понял, трудности, повторяющиеся ошибки, вопросы и рекомендации; использовать модель доступа из шага 1.
- [ ] Переходить к существующему тесту обычным способом и связывать сессию с фактической `Attempt`, в том числе когда тест уже начат. Завершение тьютора само по себе не создаёт завершённую попытку теста.
- [ ] Показывать связанный результат теста в отчёте, когда он появится. Глубокое сравнение слабых мест и ошибок оставить на следующую итерацию.
- [ ] Сохранить определения завершённых и сданных тестов, баланс звёзд, неизменяемость проверенных ответов и правила первой попытки по `stableId`. Правильность определяет только `isAnswerCorrect`; изменения попыток используют `withChildAttemptLock`.

Критерий: отчёт доступен только уполномоченному пользователю; история занятий и тестов связана, а учебный разговор не меняет баллы, звёзды или лимиты попыток.

## Следующие итерации и исключения MVP

- [ ] Разбор ошибок после теста: вопросы, ответ ребёнка, правильный ответ и связанный фрагмент материала → короткая голосовая сессия по слабым местам. Архитектура MVP должна допускать этот режим без замены тестового механизма.
- [ ] Длинные занятия: смысловые блоки и внутреннее резюме `covered`, `understood`, `weakAreas`, `currentTopic`; следующий блок получает исходный контекст и резюме вместо бесконечного накопления диалога. В MVP действует ограничение длительности.

Не входят в MVP: отдельный TTS/ElevenLabs, custom voices и детский синтезированный голос, сложная аналитика, автоматический curriculum и самостоятельное создание учебной программы. Типичные длительности из ТЗ (10–20 минут для простого материала, 20–40 для обычной темы) — ориентиры, а не обязательная продолжительность.
